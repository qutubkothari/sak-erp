## Confirmed duplication and governance problems

1. Employee Access collects employee name/code/designation/department/contact/address/biometric ID and HR email fields, then `UserService` synchronizes those fields into `employees` and can create an employee record during account creation. This creates a second HR authoring path and violates “select an existing employee.” Existing mappings cannot be guessed; any unmatched legacy account needs review before deterministic association.
2. Tenant company settings and letterhead share the same tenant `settings` JSON object; ownership/validation is not visibly partitioned at the storage boundary.
3. Email settings also own automation rules; WhatsApp automation has its own route; integration summaries duplicate the hub and static notification cards claim enabled controls without a write target.
4. Settings aliases and tabs repeat navigation for organization, company header, email configuration, and integration overview.
5. SoD uses numeric user IDs and raw role labels, with no risk/rule/resolution semantics exposed.
6. The role UI carries both module-level and screen-level grants and derives module permissions by OR-ing screen actions on save; this can flatten intentional module-vs-screen distinctions and needs a compatibility audit before modification.
7. The `roles` read endpoints are guarded but have no explicit read decorator in the controller; feature entitlement endpoints enforce Master Admin in controller code; tenant update is JWT-only at the controller. Server-side authorization consistency needs review before exposure in navigation.
8. Branch/location exists as `company_branches` but was nested in Automation. HR `employees.department` and `designation` remain text fields. Prisma Department/Plant models exist but have no API or checked-in migration and are not linked to that HR table. Legacy values need a deterministic data/release review before master selectors can replace them.

## Proposed information architecture grounded in existing functionality

- **Organization:** Tenant Profile, Documents & Branding (letterhead), confirmed organization/branch/location masters only if APIs exist.
- **People & Access:** Employee Access, Roles & Permissions, Account Security; employee identity remains in HR Master.
- **Workflow & Controls:** Segregation of Duties, existing approval/maker-checker controls exposed by current domain configuration only.
- **Business Configuration:** Production Setup and actual HR/procurement/inventory setup routes that already exist; avoid operational screens.
- **Features & Automation:** Feature Access, Mizantra AI capability index (conditional links), Email, WhatsApp, Integration Hub and real automation rules.
- **System & Governance:** Audit Trails, Master Data Governance, Continuous Controls, build/release and system health where existing data sources support them.

Search and navigation must be permission-aware; tenant entitlement/profile unavailability must remain distinct from permission denial in Super Admin diagnostics. No new generic workflow engine or master-data tables are justified by this inventory.
